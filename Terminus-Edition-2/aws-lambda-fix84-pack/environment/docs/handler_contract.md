# Handler and durable-ledger contract

The production Lambda entry point remains `/app/handler/index.mjs`. The offline simulator invokes it through `/app/handler/invoke.mjs`, which reads one event from stdin and writes the handler response to stdout. `Records` contain `messageId`, `body`, `eventSourceARN`, SQS attributes, and message attributes.

The handler reads and writes the path in `SIDE_EFFECT_LEDGER`, defaulting to `/app/data/side_effect_ledger.json`. Its public format remains a flat JSON array of committed row objects. A row contains the business identity, primary SQS message ID, immutable account/amount/currency/operation data, status, and `duplicate_message_ids`. `duplicate_message_ids` is always an array of alternate SQS message IDs for the same business event; it excludes the primary `message_id`, remains unique, and follows first successful observation order.

`business_event_id` is the durable idempotency key. Concurrent or replayed deliveries with the same immutable payload create one row. Alternate message IDs are unique, exclude the primary ID, and follow first successful observation order. Reuse of the identity with different immutable data fails closed during the cutover milestone.

Unexpected infrastructure exceptions are invocation-level failures, not record-level partial-batch failures. If any record raises one, the handler must rethrow/fail the invocation and leave the ledger unchanged for the entire batch. No peer record from that invocation may remain committed, even if it was valid or completed an asynchronous delay before the exception surfaced.

Ledger changes must survive separate Node.js processes and a process exit after the durable commit but before acknowledgement. Concurrent writers must not lose distinct rows or create duplicate business rows. The journal path is the ledger path plus `.journal`, and the lock path is the ledger path plus `.lock`. The lock file is JSON with `pid` and `created_ms`. Complete journal records are JSON lines with `seq`, `snapshot`, and `checksum`, and complete records remain on disk after a successful ledger commit as durable committed evidence.

The checksum is the SHA-256 hex digest over the compact insertion-order JSON object containing that record's sequence and snapshot: `JSON.stringify({ seq, snapshot })` with no extra spaces. Do not sort keys; nested `snapshot` object key order is the insertion order already present in the record. A truncated, uncommitted journal tail may be discarded during recovery. Corruption of a complete committed journal record must fail closed rather than interpreting state as empty. Crash injection exits after journal commit, during ledger replacement, and after ledger commit are nonzero by contract. Stale locks left by a dead process must not permanently block recovery.

The optional v2 wire form may place the immutable business fields inside `body.detail`; flat v2 bodies remain compatible. Both forms normalize to the same business payload before idempotency comparison.
