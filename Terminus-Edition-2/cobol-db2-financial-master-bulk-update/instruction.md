The overnight FNBULKUP job is supposed to reconcile fixed-width financial master updates against the local DB2 simulator, but the incident left several recovery paths unsafe. Work in the existing Go driver under `/app/internal/finbulk/runner.go` and `/app/internal/finbulk/profile.go`; keep `/app/bin/run_finbulk.sh` as the operator entry point and keep its existing `--batch`, `--input`, `--db`, `--out`, and `--abend-after` flags. The relevant operating notes are in `/app/docs/incident_timeline.md`, `/app/docs/db2_simulator_contract.md`, `/app/docs/fixed_width_layout.md`, `/app/docs/operator_log.txt`, and `/app/docs/restart_runbook.md`. The simulator is offline and deterministic, so do not add DB2 credentials, network calls, fixture-specific branches, static output files, or shortcuts that bypass the real parser and state transitions.

Before the job mutates anything, it must parse and validate the whole fixed-width file. The header and trailer batch identifiers must agree, the trailer detail count must equal the parsed detail count, the trailer BAL financial total must equal the signed BAL details, and malformed detail fields or unsupported operations must fail closed even if earlier lines looked valid. A fail-closed input or control problem exits nonzero, leaves master, risk, ledger, audit, checkpoint, applied-event, pending-lock, reject, and settlement state unchanged, and writes `summary_<batch>.json` with status `FAILED_CLOSED` under the requested output directory. Normal runs also write `rejects_<batch>.dat` and `pending_locks_<batch>.json`; when there are no rows those files should be present but empty or an empty JSON array as documented.

For valid detail records, preserve input order and the simulator semantics. A missing master row reported as SQLCODE `+100` is a business reject with fixed-width reason `MASTER_ROW_NOT_FOUND`; it is not an applied event, and later details in the same batch still run. Successful BAL details update the master, emit ledger rows, and audit the event. RAT and LIM details should produce the expected audit and applied-event records without creating BAL ledger noise. Duplicate sequence events—whether the same sequence number appears more than once within a single input file or the batch/sequence pair already exists in `applied_events` from a prior run—should be treated as already processed work and counted as skipped rather than double-posted or fatal.

The restart path must be durable. If `--abend-after` simulates an abend, only fully committed details may be persisted, the process exits with status `66`, and `summary_<batch>.json` reports `SIMULATED_ABEND`. A later run of the same batch resumes from the durable checkpoint and applied-event state without duplicating master changes, ledger rows, audit rows, or reject rows. Do not clear state or delete history to make reruns look clean. SQLCODE `-911` is retryable lock contention, not a business reject: stop at the locked detail, do not advance the checkpoint past it, do not process later records in that run, return status `75`, write `summary_<batch>.json` with `RETRYABLE_LOCK`, and write `pending_locks_<batch>.json` as a bare JSON array containing the locked account, integer sqlcode, and lock holder; the `lock_holder` value is the plain string stored at `db.locks[account]` in the simulator state file (for example `"ONLINE_POSTING_UOW_7781"`), not a nested object. Once the lock is removed, rerunning the same batch should apply the locked detail and later details exactly once.

LIM records are a single unit of work across the financial master and risk profile. Updating `master.credit_limit_cents` without the matching `risk.exposure_limit_cents` change is the bug to avoid. If either side of a LIM detail hits `+100`, `-911`, or `-530`, roll back the whole LIM detail and leave no applied marker for it; `-530` is a business reject, while `-911` remains retryable lock contention. A valid LIM detail commits both tables together and writes one coherent audit record and applied marker.

Add optional support for `--control PATH` without breaking invocations that omit it. The control manifest is JSON with `batch_id`, `business_date`, `source`, `expected_detail_count`, and `expected_financial_total`, and may also carry an optional `prior_batch_id` declaring the expected chain tip on the same business date. When present, validate each field against the parsed batch before accepting the work: `batch_id` must equal the header batch identifier, `business_date` must equal the header business date field, `source` must equal the header source field, `expected_detail_count` must equal the parsed detail count, and `expected_financial_total` must equal the BAL-only signed total. After a successful controlled run, persist `control_totals[batch_id]` with status `SETTLED`, integer detail count and financial total, the input SHA-256, and the identifying batch id, business date, and source. A same-hash controlled rerun is idempotent and should report the bypassed detail count in integer field `skipped`; a different input hash for an already settled batch id must fail closed without overwriting the prior settlement record or mutating simulator state.

Extend the controlled path with a tamper-evident settlement chain and a separate close ceremony. Every settled batch must also record `prior_chain_sha256` (the previous settled batch's `chain_sha256` for the same `business_date`, or 64 ASCII zeros for the first batch of the date), `chain_sha256` equal to lowercase hex `sha256(prior_chain_sha256 || batch_id || input_sha256 || business_date)`, and `prior_batch_id` (or `null`). Maintain `chain_index[business_date]` as an ordered array of settled batch ids; idempotent same-payload reruns must not append a duplicate or change any chain field. When a manifest carries `prior_batch_id`, it must equal the current chain tip for that date or the run fails closed (`FAILED_CLOSED` with `error` containing `UNMET_DEPENDENCY`) without mutating state. Every mutating run must hold an exclusive `flock` on `<dirname(db)>/.lock_<batch_id>` for its full critical section; a concurrent same-batch invocation exits with status `73` and summary `BATCH_BUSY` after writing the three standard output files empty, without touching simulator state. A new `--abend-after-lim-master` flag aborts mid-LIM after the master credit-limit half commits but before the risk exposure half commits; the runner must roll the in-process master half back so durable state shows neither half applied, write summary `SIMULATED_ABEND`, and exit `66`, with a rerun applying that LIM exactly once across both tables. Finally, `--close DATE` (in place of `--input` and `--batch`) walks `chain_index[DATE]` in order, recomputes each link, and writes `close_<DATE>.json` (status `CLOSED`, `chain_root`, ordered `batches` array) plus a fixed-width `glfeed_<DATE>.dat` with header, one `G` record per batch, and trailer; chain breakage produces summary status `CLOSE_BROKEN` with an empty feed, while a date with no settled batches produces a `CLOSED` summary and a zero-byte feed. Close mode is read-only, never acquires a per-batch lock, and never mutates simulator state.
