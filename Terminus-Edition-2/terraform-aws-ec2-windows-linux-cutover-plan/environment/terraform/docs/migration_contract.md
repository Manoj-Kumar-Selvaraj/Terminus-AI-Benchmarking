# EC2 Windows-to-Linux migration contract

The Terraform root at `/app/environment/terraform` is only a planning workspace. It must not read from AWS, use data sources, import resources, apply changes, or depend on real credentials. The root configuration supplies the offline AWS provider and inventory in `migration.auto.tfvars.json`; the EC2 replacement design belongs in `modules/ec2_linux_migration` and must be consumed through the existing `module "ec2_linux_migration"` block. The operator command `/app/environment/scripts/render-migration-plan` runs `terraform init -backend=false`, `terraform validate`, `terraform plan -refresh=false`, and `terraform show -json`, then writes `/app/output/ec2_linux_migration_plan.json`.

All Terraform under `/app/environment/terraform` must be canonical HCL that passes `terraform fmt -check -recursive` before the verifier runs. Run `terraform fmt -recursive` locally before submitting.

Every legacy Windows workload in `legacy_windows_instances` needs one Linux `aws_instance` using the supplied target AMI, instance type, private subnet, availability zone, private IP, and root disk size from `root_gib`. Instances remain private with `associate_public_ip_address=false`, keep every planned EC2 address under `module.ec2_linux_migration`, and preserve the workload identity tags in the plan: `Name`, `ManagedBy`, `MigrationProgram`, `ComplianceDomain`, `CutoverId`, `MigrationWave`, `MigratedFromOS`, `OSFamily`, `LegacyInstanceId`, `Workload`, `Application`, `Environment`, `Owner`, `OwnerCostCenter`, `PatchGroup`, and `BackupTier`. `MigratedFromOS` is `windows`, `OSFamily` is `linux`, and `ManagedBy` remains `terraform`. Each instance `root_block_device` must set `tags` with `VolumeRole = "root"` plus the same migration identity tags visible on the root gp3 disk in plan JSON.

Each `data_volumes` inventory entry becomes one encrypted gp3 `aws_ebs_volume` restored from its snapshot in the workload availability zone and one `aws_volume_attachment` to the matching Linux instance with the exact Linux device name. Keep the documented IOPS, throughput, size, snapshot ID, workload, volume role, source legacy instance, `DeviceName`, `SourceSnapshot`, `VolumeRole`, application, environment, owner, patch group, backup tier, and migration tags visible in the Terraform plan JSON. Every attachment uses `force_detach=false`.

Access is SSM-first. Include `migration_defaults.required_ssm_security_group`, use `migration_defaults.iam_instance_profile`, omit `key_name`, and filter out all groups in `migration_defaults.forbidden_admin_groups`; the inventory intentionally still contains legacy RDP, WinRM, and domain-join groups. EC2 Instance Metadata Service must keep the endpoint enabled, require tokens, use hop limit one, and expose instance tags. Termination protection, detailed monitoring, EBS optimization, root and data KMS encryption, and migration tags all follow `migration_defaults`.

## Plan JSON observability

The generated JSON exposes `configuration.root_module.module_calls`, `resource_changes[*].change.after`, and `planned_values.outputs`. The root outputs are `planned_linux_instances` and `planned_data_volumes`; their `value` objects are keyed by workload and by `workload:device_name` respectively. The supplied inventory contains exactly four legacy Windows workloads and exactly five restored data volumes. The data volume output keys are `payments-api:/dev/sdf`, `payments-api:/dev/sdg`, `claims-worker:/dev/sdf`, `report-export:/dev/sdf`, and `admin-jump:/dev/sdf`. The exact shared values are `ssm-linux-core-prod`, `windows-to-linux-2026`, `payments-platform`, `CUT-2026-06-WINLINUX`, and `wave-3-prod-parallel`. Boolean hardening values are `true` for termination protection, detailed monitoring, EBS optimization, root and data encryption, and `false` for public IP association and attachment force detach. Metadata endpoint and instance tag visibility use `enabled`, while IMDS token enforcement uses `required`.
