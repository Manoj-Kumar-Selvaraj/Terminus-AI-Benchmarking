### Jenkins controller auto-upgrade recovery

The Jenkins controller auto-upgrade selected a target release that cannot boot with the runtime still deployed. Do not patch the incident fixture directly. Build a reusable Go recovery controller at `/app/recovery/main.go`, invoked by `/app/scripts/jenkins-recover`, and make it work from the offline incident data under `/app/evidence`, `/app/docs`, `/app/cluster`, `/app/config`, `/app/backups`, and `/app/jenkins_home`.

The controller must support `inspect --json`, `plan --json`, `apply --owner OWNER [--fault POINT] [--hold-ms MS]`, `resume --owner OWNER [--fault POINT] [--hold-ms MS]`, and `verify --json`. Owner prefixes define the recovery boundary: `operator-*` stops after runtime recovery, `restore-*` stops after home recovery, `plugins-*` stops after plugin recovery, `policy-*` stops after upgrade-policy recovery, and `cluster-*` or any other prefix runs full recovery through cluster start.

Treat `/app/docs` as the recovery contract. The docs define the required JSON shapes, runtime compatibility rules, backup validation, plugin resolution, policy safety, journal and lease behavior, fault points, owner fencing, idempotent replay, cluster election, and simulator usage. `plan --json` must be read-only but still validate the requested scope, including plugin resolver failures and dependency cycles. Plugin plans must expose resolved plugin versions on the relevant action as `actions[].resolved`. `verify --json` must only run diagnostics. Full cluster recovery must start the simulator through `JENKINS_SIM_BIN` when set, otherwise through `/app/scripts/jenkins_cluster_sim`, passing `APP_ROOT` to the child process and never writing simulator outputs directly.
